> （cell 是由 nbclient 另外 spawn 的 kernel 執行，kernel 沒有 `-I`，會吃 `PYTHONPATH=/tmp/pglib`）

> 這個 namespace 沒有 NetworkPolicy，對 PyPI 的 egress 是通的。

## OOM 情境結果（重點，對照 F11）

設定：`KERNEL_MEMORY_LIMIT=6Gi`（即 `RLIMIT_DATA` = 6Gi，比配置量大，所以不會先觸發 `MemoryError`）、
Pod `limits.memory=4Gi`，在容器內以 bigred 身分（套用 venv 的 activate）配置並觸碰 5 GB。

實測（`test/e2e/out/oom-cgroup.log`）：

```
memory.oom.group = 1
memory.max       = 4294967296  (= 4Gi)
restartCount     = 0 -> 1
lastState.reason = OOMKilled
RESULT           = WHOLE_POD_KILLED
```

**結論：整個 Pod（容器）被 OOM 殺掉並重啟**，不是只殺配置記憶體的那個程序。容器 cgroup 的
`memory.oom.group=1`，加上 kubelet 沒有設 `singleProcessOOMKill`，所以 cgroup v2 的 OOM killer
會把整個 cgroup 裡的所有程序一起殺掉（含 PID 1），kubelet 隨即重啟容器。

**與 spec F11 對照：一致，F11 不需要修改。** F11 說「tk8s 是 v1.37.1、cgroup v2，沒有設定
`singleProcessOOMKill`，所以容器 OOM 時整個被殺（`memory.oom.group`）」，本次實測完全吻合
（`memory.oom.group=1`、`lastState=OOMKilled`、容器重啟）。這也印證 spec 第 5 節與風險表的說明：
同一個 Pod 內一個人把記憶體吃爆，會波及所有人的桌面，因此要靠閒置回收、狀態列用量顯示與文件
提醒來降低機率，需要強隔離時改用 JupyterHub。

- `test/e2e/run.sh` 的 EXIT trap 會刪掉 `rdp-jupyter` 與 `rdp-jupyter-e2e-data` 兩個 namespace
  （`--wait=false`，不卡住退出）。跑完以 `kubectl get ns | grep rdp-jupyter` 確認沒有殘留。
- 本次執行後已確認 tk8s 上**沒有任何 `rdp-jupyter*` namespace** 殘留。
- 節點上的映像檔副本（見上）**不會**被 run.sh 清除，需要時依上面的 `crictl rmi` 手動處理。
